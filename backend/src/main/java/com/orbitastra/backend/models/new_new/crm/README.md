# CRM collection model mapping

This package contains the inquiry and admission pipeline for one school tenant.
Every top-level collection model extends `SchoolBase`, so every record inherits:

- `id`: MongoDB document identity.
- `schoolId`: tenant boundary.
- creation and update audit fields.
- record lifecycle fields.
- optimistic-lock `version`.

All references are stored as string document ids. The models intentionally do
not use MongoDB `DBRef`. Every repository query must include `schoolId` so that a
reference supplied by one school cannot access another school's record.

## Relationship overview

```text
AcademicYear.name
        |
        +-----------------------+
        |                       |
        v                       v
AdmissionCycle             Inquiry
        |                       |
        | contains              | contains
        v                       +--> InquiryGuardian[]
IntakeCapacity[]                +--> InquiryFollowUp[]
        |                       |
        +-----------+-----------+
                    |
                    v
          AdmissionApplication
                    |
              +-----+------+
              |            |
              v            v
      AdmissionReview   AdmissionOffer
                               |
                               v
                            Student
```

## Top-level collections

### Inquiry — `inquiries`

Represents an admission lead before a formal application exists.

| Field | Links to / purpose |
|---|---|
| `schoolId` | Inherited tenant boundary. |
| `inquiryNo` | School-scoped business number generated using `NumberSequence`. |
| `academicYear` | `AcademicYear.name`, for example `2026-2027`; never an AcademicYear document id. |
| `interestedClassDocsId` | Future final class/grade document id. |
| `assignedCounselorDocsId` | Staff document responsible for the lead. |
| `guardians` | Embedded prospective guardian snapshots. |
| `followUps` | Embedded CRM interaction timeline. |
| `nextFollowUpAt` | Denormalized current next action used by counselor dashboards. |

An Inquiry does not store an application id. Applications are found using:

```text
AdmissionApplication.schoolId = Inquiry.schoolId
AdmissionApplication.inquiryDocsId = Inquiry.id
```

### AdmissionCycle — `admission_cycles`

Defines when one school's applications open and close for one academic year.

| Field | Links to / purpose |
|---|---|
| `academicYear` | `AcademicYear.name`. |
| `name` | Human-readable cycle name; unique with `schoolId` and `academicYear`. |
| `applicationFormDefinitionDocsId` | Optional future versioned admission-form definition. |
| `capacities` | Embedded class seat configurations. |

The cycle does not store application ids. Applications are queried using
`schoolId + admissionCycleDocsId`.

### AdmissionApplication — `admission_applications`

Represents the formal application and is the source of truth for the applicant's
admission pipeline state.

| Field | Links to / purpose |
|---|---|
| `applicationNo` | School-scoped business number generated by `NumberSequence`. |
| `admissionCycleDocsId` | Required link to `AdmissionCycle.id`. |
| `inquiryDocsId` | Optional link to `Inquiry.id`; null for a direct application. |
| `appliedClassDocsId` | Requested class/grade document id. |
| `guardians` | Submission-time guardian snapshots. |
| `applicationFormDefinitionDocsId` | Form definition used when the application was submitted. |
| `applicationFormVersion` | Exact version of that form definition. |
| `formAnswers` | Submitted answers interpreted using the form definition and version. |
| `evidenceDocumentDocsIds` | Links to uploaded document records. |
| `assignedAdmissionOfficerDocsId` | Staff member managing the application. |
| `resultingStudentDocsId` | Student created when the application reaches `ENROLLED`. |

Guardian and applicant fields are snapshots. Changing an Inquiry after submission
must not silently rewrite an already-submitted application.

### AdmissionReview — `admission_reviews`

Stores one review assignment and its result. One application can have multiple
reviewers and review rounds.

| Field | Links to / purpose |
|---|---|
| `admissionApplicationDocsId` | Required link to `AdmissionApplication.id`. |
| `reviewRound` | Review iteration number. |
| `reviewerDocsId` | Reviewing staff document id. |
| `reviewerRole` | Role used by that reviewer for this decision. |
| `criterionScores` | Per-criterion scores such as interview and entrance test. |

Reviews are queried using
`schoolId + admissionApplicationDocsId`. The application does not store a review
id array.

### AdmissionOffer — `admission_offers`

Stores one revision of a formal offer issued for an approved application.

| Field | Links to / purpose |
|---|---|
| `offerNo` | School-scoped business number generated by `NumberSequence`. |
| `revisionNo` | Revision number unique within one application. |
| `admissionApplicationDocsId` | Required link to `AdmissionApplication.id`. |
| `offeredClassDocsId` | Class/grade being offered. |
| `offerDocumentDocsId` | Generated offer document record. |
| `acceptanceSignatureDocsId` | Stored acceptance-signature record. |
| `depositInvoiceDocsId` | Admission deposit invoice. |
| `issuedByDocsId` | Staff member who issued the offer. |

Applications do not store offer-id arrays. Offers are queried using
`schoolId + admissionApplicationDocsId`.

## Embedded value objects

Embedded objects have no collection, `id`, or `schoolId`. Their tenant and
lifecycle are inherited from the parent document.

### InquiryGuardian

Stored inside `Inquiry.guardians` and `AdmissionApplication.guardians`.
Before persistence, the service should store phone numbers in normalized E.164
format and email addresses in trimmed lowercase form.

### InquiryFollowUp

Stored inside `Inquiry.followUps`. `counselorDocsId` links to a staff document.
When a follow-up becomes the current next action, its `nextFollowUpAt` is also
copied to `Inquiry.nextFollowUpAt` for indexed dashboard queries.

### IntakeCapacity

Stored inside `AdmissionCycle.capacities`. `classDocsId` links to the class/grade
document. Only configured limits are stored.

Offered, enrolled, and waitlisted totals are calculated from applications using:

```text
schoolId + admissionCycleDocsId + appliedClassDocsId + status
```

This avoids mutable counters becoming inconsistent or turning AdmissionCycle
into a high-contention document.

## Workflow and status linking

```text
Inquiry.NEW
  -> Inquiry.CONTACTED
  -> Inquiry.APPLICATION_STARTED
  -> Inquiry.APPLICATION_SUBMITTED

AdmissionApplication.DRAFT
  -> SUBMITTED
  -> UNDER_REVIEW
  -> APPROVED / REJECTED / WAITLISTED
  -> OFFERED
  -> OFFER_ACCEPTED
  -> ENROLLED

AdmissionOffer.DRAFT
  -> ISSUED
  -> ACCEPTED / DECLINED / EXPIRED / WITHDRAWN
```

When enrollment finishes, the service must atomically coordinate:

1. create the Student;
2. set `AdmissionApplication.resultingStudentDocsId`;
3. set the application status to `ENROLLED`;
4. set the accepted offer status and response;
5. close the originating Inquiry when one exists.

These are service-level transactional rules, not entity validation.

## Where validation belongs

The collection models contain only required persistence invariants such as
`@NotBlank` and `@NotNull`. Request-specific rules belong in API request DTOs,
including:

- text length and formatting;
- email and phone validation;
- score and seat ranges;
- chronological date validation;
- valid status transitions;
- form-answer validation;
- conditional fields such as withdrawal reasons;
- authorization and cross-school reference checks.

MongoDB collection validators and indexes should be created through controlled
database migrations for production. Java annotations alone are not a substitute
for database-level constraints.
